# 0005. 크레딧은 추가 전용 원장 + 멱등 키

## 맥락
요금은 플랜 구독(토스페이먼츠 자동결제)과 크레딧(영업 브리핑 생성 1회 = 3크레딧, 플랜 월 지급 + 충전 팩)으로 나뉩니다. 동시 요청, 결제 웹훅 재전송, 사용자의 더블 클릭이 모두 현실적인 위험입니다.

## 결정
- `credit_ledger`는 **추가만** 합니다(지급·사용·만료·환불 모두 행 추가). 잔액은 `organizations.credit_balance`에 캐시하되, 같은 트랜잭션에서 `SELECT … FOR UPDATE`로 잠그고 원장 행과 함께 갱신합니다. DB `CHECK (credit_balance >= 0)`가 마지막 방어선입니다.
- 모든 원장 행은 **멱등 키**(유니크)를 가집니다: 플랜 지급 `grant:{org}:{plan}:{기간}`, 브리프 사용은 클라이언트가 보낸 `Idempotency-Key`. 같은 요청의 재시도는 새 행을 만들지 않고 이전 결과를 돌려줍니다.
- 우리 쪽 `orderId`로 결제 행을 먼저 만든 뒤, 그 `orderId`를 토스 `Idempotency-Key`로 붙여 승인을 호출합니다. 토스의 결제 상태 변경 웹훅이 오면 `orderId`로 조회해 결제 행을 **대사(reconcile)** 합니다.
- 빌링키는 Fernet으로 암호화해 저장합니다. 갱신 실패는 1·3·7일 후 재시도(dunning) 후 무료 플랜으로 내립니다.

## 결과
- 얻은 것: 잔액이 틀렸을 때 원장으로 재계산·감사할 수 있습니다. 동시 사용 테스트(`test_concurrent_spends_cannot_overdraw`)가 음수 잔액이 불가능함을 보여 줍니다.
- 치른 비용: 원장 행이 계속 늘어납니다(조직당 월 수십 행 수준이라 문제 없음).
