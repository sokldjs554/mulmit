# 0010. 쿼리는 운영 규모 데이터에서 측정하고 고친다

## 맥락
데모 데이터는 수백 행이라 모든 쿼리가 빠르고 모든 실행 계획이 순차 스캔입니다. 인덱스 설계가 맞는지, 근사 인덱스가 결과를 줄이지 않는지는 그 규모에서 보이지 않습니다.

## 결정
- `manage bench`로 별도 DB에 공고 10만·신호 40만·청크 60만·추천 30만 건을 만들고, 앱의 핫 쿼리를 **최초 스키마(0001)와 현재 스키마(head)에서** `EXPLAIN (ANALYZE, BUFFERS)`로 비교합니다. 벡터 검색은 인덱스 없이 전체 정렬한 정확한 결과와 비교해 재현율을 잽니다. 결과는 [docs/performance.md](../performance.md).
- 측정으로 찾은 것과 조치(마이그레이션 0002):
  1. **추천 후보 벡터 검색이 결과를 잃음**: "진행 중 공고 중 가장 가까운 300건"이 전체 테이블 HNSW 인덱스를 타면, pgvector는 인덱스가 찾은 `hnsw.ef_search`(기본 40)건에 **나중에** 상태 필터를 적용해 13건(재현율 4%)만 돌려줬습니다. 수정 후 300건, 재현율 100%입니다. → 진행 중 공고만 담은 **부분 HNSW 인덱스**와 요청 건수만큼의 `SET LOCAL hnsw.ef_search`. 부분 인덱스가 캐시된 일반 실행 계획에서도 쓰이도록 상태 조건은 바인드 변수가 아닌 리터럴로 씁니다.
  2. **참조번호 조회가 신호 전체를 스캔**: 발주계획·사전규격 번호로 기존 기회를 찾는 `external_refs @>`가 조회당 87ms(신호 40만 건). 수정 후 0.1ms 미만. → `jsonb_path_ops` GIN 인덱스.
  3. **키워드 후보가 인덱스를 못 씀**: `'키워드' = ANY(keywords)` → `keywords @> ARRAY['키워드']` + GIN. 제목 트라이그램 인덱스와 BitmapOr로 합쳐집니다.
  4. **운영 개요가 가장 큰 테이블을 두 번 스캔** → `count(*) FILTER (...)` 한 번으로(173ms → 124ms).
  5. 전체 테이블 HNSW 인덱스 2개는 삭제했습니다. 이제 쓰는 쿼리가 없고, 기회 연결처럼 **정확해야 하는** 쿼리에서 플래너가 근사 인덱스를 고르면 후보가 조용히 빠질 수 있으며, 임베딩을 쓸 때마다 그래프 갱신 비용이 듭니다.
- 인덱스는 `CREATE INDEX CONCURRENTLY`로 만들어 배포 중에도 쓰기를 막지 않습니다(데이터가 있는 상태에서 4초).
- 1번은 규모에서만 드러나므로, 플래너가 그 경로를 타도록 강제한 **회귀 테스트**를 두었습니다(`ef_search` 설정을 빼면 실패함을 확인).

## 결과
- 얻은 것: 대용량에서의 정확성 버그 하나와 병목 두 개를 배포 전에 찾았습니다. 쿼리를 바꿀 때 같은 명령으로 전후를 비교할 수 있습니다.
- 치른 비용: 합성 데이터의 분포(주제별로 뭉친 벡터, 균등한 기관 분포)는 실제와 다릅니다. 실제 데이터가 쌓이면 `pg_stat_statements` 상위 쿼리로 대상을 다시 고릅니다.
